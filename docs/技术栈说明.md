# 技术栈说明

## M4 当前增补（2026-11-13）

M4 沿用现有栈，无新增运行依赖。长期记忆为 PostgreSQL 结构化筛选，最多注入 8 条已确认且岗位/模式匹配的条目；没有向量库。摘要为确定性主题覆盖和有效数值汇总，无额外摘要模型调用。趋势使用可读条形图按版本分组，无跨版本提升结论。

下方 M1/M2/M3 章节为历史基线，未来契约与当前实现的差异以本节、M4阶段报告和实际 OpenAPI 为准。

## M3 实际技术增量

沿用 Vue 3 / TypeScript / Vite / Pinia 与 FastAPI / Pydantic / SQLAlchemy / psycopg / Alembic / PostgreSQL:6543。新增运行依赖 HTTPX，直接调用 DeepSeek Chat Completions SSE + JSON 模式；未引入 LangChain、LangGraph 或向量库。四 Skill 是项目自己的轻量 Python 能力模块，有触发、执行逻辑、领域锚点和严格输出契约。

后端执行器线程内使用同步 HTTPX 流式客户端，逐事件检查取消和时间预算，网络 I/O 不持有会话行锁。Pydantic 校验五维结构和范围，项目语义校验原文引用，Decimal 使用 ROUND_HALF_UP 计算与汇总。前端使用可读条形图及原文定位链接，无 ECharts 雷达依赖，也不由维度图反算总分。依赖实际解析版本以两端锁文件为准，API/包版本 0.3.0。

已按 [DeepSeek 官方 Chat Completions 文档](https://api-docs.deepseek.com/api/create-chat-completion/) 核对模型参数与流格式（2026-11-13）；官方域名发送 thinking.disabled，忽略 reasoning_content。模型接口支持 HTTPS 兼容地址，但本轮仅实测官方 DeepSeek，不能宣称其他服务均兼容。

## M2 选型落地

M2 沿用既有锁文件，没有引入新框架。使用标准 ThreadPoolExecutor、SQLAlchemy 独立 Session、PostgreSQL advisory/行锁与部分唯一索引，实现单实例操作执行；FastAPI StreamingResponse 输出持久化 SSE，浏览器使用 fetch 读取并携带 Bearer 和 Last-Event-ID。

当前 llm/mock.py 为固定数据/规则实现，没有真实 HTTP 模型、工具调用或长期记忆。真实模型和 ECharts 等仍留待后续。SQLAlchemy Session 不跨线程共享；网络流不长期持有鉴权连接。


状态：设计基线 v0.1，2026-11-13。M1/M2 的前后端、数据与 Mock 操作层已实现；真实 Agent、ECharts、模型与自动化浏览器测试留待后续。

## 1. 选型

| 层 | 技术 | 选择理由 | 本项目边界 |
|---|---|---|---|
| UI | Vue 3、Composition API、TypeScript | 组件化、显式类型、适合面试与报告界面 | 不混用 React |
| 构建 | Vite、npm | 本地开发与静态构建 | 首次实施后提交 package-lock.json |
| 状态 | Pinia、Vue Router | 当前身份、资料、会话状态与路由分离 | 服务端才是面试状态事实来源 |
| 组件/图表 | Element Plus、ECharts、定制 CSS | 配置表单、交互反馈、维度图与趋势 | 图表同时提供文字结果 |
| API | FastAPI、Pydantic | 请求/输出校验、OpenAPI、流式传输 | 不在路由内堆积业务或 Prompt |
| Python 管理 | uv、pyproject.toml | 独立环境和锁定依赖 | 不改系统 Conda 环境；uv 已装于项目内独立引导环境 |
| ORM | SQLAlchemy 2.x、psycopg 3 | PostgreSQL、事务、关系映射 | 首版同步 Session；同步 I/O 不阻塞异步事件循环 |
| 迁移 | Alembic | 版本化数据库结构 | 迁移是建表唯一来源 |
| 数据库 | PostgreSQL 17 系列 | 事务、UUID、JSONB、并发与约束 | 所有连接端口 6543，不配置 SQLite 回退 |
| 模型 | DeepSeek HTTP API、httpx、自有接口 | 简化依赖并保留替换空间 | 模型名由配置决定，不锁死已过时名称 |
| 流式输出 | SSE＋fetch | 生成进度、文本增量、取消和鉴权 | 使用 fetch 读取流，支持 Authorization 头 |
| 测试 | pytest、httpx TestClient、Playwright | 规则、API、浏览器流程 | 不把 Mock 成绩当真实效果 |
| 编排 | 可选 Docker Compose | 后续部署 PostgreSQL 与应用 | 当前 Compose 已实现 db，应用容器化待后续 |

## 2. 版本策略

建议实现起点：Node.js 22 或 24、Python 3.12、PostgreSQL 17；这不是“最新版”声明。前端 Vue 主版本为 3，SQLAlchemy 使用经验证的 2.x 版本。首次实现先验证依赖兼容性，再锁定精确版本并记录。

当前机器只做过工具版本读取：Python 3.13.9、Node v24.13.0、npm 11.6.2、Git 2.48.1.windows.1；找到 docker.exe，但没有检查守护进程。当前使用项目本地 uv；psql 通过专属 PostgreSQL 容器执行。M1 已验证依赖、数据库与应用就绪；精确版本见锁文件。

## 3. 架构取舍

- 单个后端应用内分层，不拆微服务；四个 Skill 是能力模块，不要求四个并行 Agent。
- 状态机决定流程，模型输出候选问题、评价、摘要；后端负责规则约束、总分和持久化。
- 使用 PostgreSQL JSONB 保存结构化维度、配置和版本快照；核心关系仍用外键和独立表。
- 记忆首版采用用户、类型、主题、更新时间的结构化检索，不以向量检索作为前提。
- 模型评价与用户画像事实分离；推断记忆可供确认和纠正，不自动改写用户明确提供的经历。
- 同步数据库会话仅在短事务中使用；流式 API 的模型 HTTP 调用采用异步客户端，阻塞数据库步骤经受控线程执行，禁止跨线程共享 Session。
